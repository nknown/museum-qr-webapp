# MIYP performance evaluation

This package reproduces the two-sided measurement setup used to evaluate MIYP.
The requester records the experience generated by synthetic anonymous visitors;
the server monitor records how the deployed host and its Compose services react.
Both sides use UTC timestamps so their outputs can be aligned after a run.

The tools target public User Device presentation URLs. They do not require an
administrator or curator account, but they create the same presentation
sessions and access records as ordinary anonymous visits.

## Contents

- `load_test.py` generates visitor journeys and records request latency, status,
  transferred bytes, slide events, throughput, and requester host utilisation.
- `browser_data.py` uses headless Chrome to measure cold- and warm-cache transfer.
- `requester/` contains the general launcher and the two experimental profiles.
- `server/monitor_server.sh` samples host, container, proxy, and database state.
- `cleanup_sessions.py` previews or removes database rows created by a run.
- `config/` contains safe examples rather than deployment addresses or UUIDs.
- `results/` is intentionally ignored except for its placeholder.

See [requester/README.md](requester/README.md) and
[server/README.md](server/README.md) for commands and output definitions.

## Reproduction workflow

Use two machines for capacity experiments: the application server and a
separate requester. Running both roles on one host makes requester CPU, memory,
and network activity compete with the application and weakens the result.

1. Start the MIYP Compose deployment on the application server.
2. Copy `config/benchmark.env.example` to `config/benchmark.env` and configure
   local addresses and certificate trust.
3. Copy `config/presentations.example.txt` to `config/presentations.txt` and
   replace the placeholders with published presentation paths.
4. Start `server/monitor_server.sh` on the application server.
5. Start one requester profile on the separate requester machine.
6. Retrieve the matching directories under `results/requester/` and
   `results/server/`. Their names and internal records use UTC timestamps.
7. Run `validate_results.py` and retain the configuration alongside analysed
   results so the workload can be reproduced.

## Installation

Create an isolated environment on the requester and install only the benchmark
dependencies:

```bash
python3 -m venv .benchmark-venv
source .benchmark-venv/bin/activate
python -m pip install -r benchmarks/requirements.txt
```

Chrome or Chromium and OpenSSL are additionally required for the browser
transfer measurement. The load experiments themselves require only Python and
the packages in `requirements.txt`.

## Data handling

Generated result files are not source code and are excluded from Git. In
particular, `load_test.py` writes session identifiers used by
`cleanup_sessions.py`; these identifiers must not be published. Result JSON can
also contain hostnames, target URLs, and certificate fingerprints. Sanitize any
dataset before publishing it as a release or research artifact.

Never place private keys, environment files, real OAuth credentials, database
dumps, raw application logs, or private presentation lists in this directory.

## Scope and interpretation

The scripts generate accelerated and controlled workloads. They are useful for
comparison, saturation discovery, and regression testing, but they do not by
themselves prove the exact number of real museum visitors a deployment can
serve. Report the hardware, service versions, workload profile, think times,
network conditions, and any other activity on both hosts with every result.
